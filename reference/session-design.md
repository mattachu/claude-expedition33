# Session Design

Architecture and design reference for the Clair Obscur: Expedition 33 AI session system.  
Fetch when understanding the system structure, rationale, or constraints is needed.  
Operational procedure is in `reference/session-procedure.md`.

---

## Core Principle

Claude does all content generation. Scripts handle mechanical file operations. Matt only pushes.

---

## File Architecture

### Folder structure

```
overview/          ← overview file, progress tracker, party summary (generated), Pictos/Lumina summary (generated)
data/              ← JSON source-of-truth files for playthrough, characters, skills, weapons and Pictos/Lumina
characters/        ← narrative character files for each character
reference/         ← reference files for game mechanics, full Pictos/Lumina catalogue, session procedure and design and historical errors
scripts/           ← scripts for updating files, handling chat transcripts, and managing the repo
chats/             ← chat transcripts, with indexes and smaller part files for each chat
.github/workflows/ ← generate-links.yml (auto-generates LINKS.md and scripts.md on push)
```

### LINKS.md

Auto-generated by GitHub Actions on every push to main. Contains jsDelivr URLs for all repo files pinned to the commit hash of that push. Matt pastes the contents of `LINKS.md` at session start; Claude extracts all file URLs and fetches individual files on demand.

### Data files (JSON source of truth)

- `data/characters.json` — per-character structured state: level, attributes, stats (base and modified), weapon equipped (name only), pictos equipped (names), LP, lumina exclusions/extras, skills equipped/learned, gradient skills
- `data/playthrough.json` — act, phase, current area, active/reserve party, inventory, phase checklist
- `data/pictos-lumina.json` — Pictos catalogue (194 entries); `equipped_by` field is single source of truth for Pictos assignments
- `data/skills.json` — full skill reference per character: AP cost, effects, character-specific fields (stance_change, rank_bonus, stains, wheel/mask)
- `data/weapons.json` — full weapon inventory per character: level, power, element, scaling, effects, obtained/future/rejected flags

### Generated files

`scripts/generate.py` reads the JSON files and regenerates content in two ways:

- **Whole files:** `overview/party-summary.md`, `overview/pictos-lumina-summary.md`, `reference/pictos-lumina-catalogue.md` are regenerated in full
- **Embedded blocks:** `GENERATED:START` / `GENERATED:END` marker blocks within other files (e.g. per-character stats blocks in `characters/*.md`) are regenerated in place

The updater script (`apply_changelist.py`) calls `generate.py` automatically after applying all `DATA:` and `FILE:` blocks.

### Boundary markers

Generated sections in Markdown files are wrapped:
```
<!-- GENERATED:START source:field -->
...generated content...
<!-- GENERATED:END -->
```

The updater script checks for `GENERATED:` marker overlap when applying `FILE:` blocks. Three cases:

- **No markers in old or new content:** proceeds silently
- **Same marker keys in old and new:** proceeds automatically, with a note that `generate.py` will refill the markers after the changelist is applied
- **Marker keys differ (added, removed, or renamed):** warns loudly and requires interactive confirmation; aborts if running non-interactively

The practical implication: a `FILE:` block that preserves existing `GENERATED:` marker keys is safe and will proceed automatically. A `FILE:` block that adds, removes, or renames marker keys requires explicit confirmation.

## File Roles

### Transcript file

A single Markdown file (`chatN.md`) written incrementally during the session via `!log`. Contains the verbatim record of all turns — Matt's and Claude's alike — divided into sections by `<!-- SECTION -->` markers. This is the primary source of truth for the end-of-session pass.

### Index file

A single Markdown file (`chatN-index.md`) created in full at end-of-session. Contains part file links, a table of contents with section titles and descriptions, and a timestamp. Used by Matt for navigation (jump links into the transcript) and by Claude to identify which part file to fetch when looking something up from a previous session. Not written to incrementally during the session.

### Section markers

Claude inserts a bare marker in the transcript at the start of each new section during `!log`:

```
<!-- SECTION -->
```

The marker is a plain HTML comment with no title embedded — invisible when rendered, unambiguous to parse. Section titles are added in the end-of-session pass. The `^<!-- SECTION -->$` pattern (anchored) is used by `csplit` to split on true section boundaries only — the marker text appears elsewhere in the transcript in discussions about the system, so anchoring is essential.

### Part files

The transcript is split into part files at end-of-session by the Sonnet pass, grouping sections to approximately 500–600 lines per part. Part files are for Claude to read in future sessions — loading only the relevant part keeps token consumption low. The boundary points are irrelevant to Matt.

Note: `scripts/split_transcript.py` exists and performs the same function mechanically. It is not used in the current workflow (Sonnet creates part files directly) but is available as a fallback.

### Session state

There is no session state file in the current workflow. All decisions, data changes, and in-game actions are captured verbatim in the transcript and extracted by the end-of-session pass. `ACTION:` flags in Claude's responses serve as lightweight markers to assist this extraction.

## Character File Update Approach

Character files (`characters/*.md`) and data files (`data/*.json`) are the two layers of character state. JSON files are the source of truth for structured data; character Markdown files contain narrative context, build rationale, and notes. Changes to either are captured in the transcript and extracted by the end-of-session pass as `DATA:` or `FILE:` blocks in the changelist.

**When to load files mid-session:**

- **Load the character Markdown file** when the session involves structural changes to build rationale, extended notes, or anything requiring the full narrative context of the character file.
- **Load the relevant JSON file(s)** when precise current values are needed — LP budgets, stat totals, exact skill/weapon details, Pictos assignments — or when answering data-driven queries that require scanning structured records (e.g. "which ten Pictos give the highest Speed boost"). The overview summaries are condensed; fetch the JSON when the summary isn't sufficient or when a query requires systematic comparison across entries.
- **Load neither** for minor changes or quick decisions — capture via `ACTION:` flag and let the end-of-session pass fetch and update.

**Decision rule:** if a change can't be fully specified from what's already in context, fetch the relevant file mid-session rather than working from incomplete information. The end-of-session pass fetches files it needs regardless — mid-session fetching is about having accurate data during discussion, not about reducing end-of-session work.

## Changelist Format

Three block types: `DATA:` (JSON updates), `FILE:` (Markdown section replacements/insertions), and `APPEND:` (raw append to end of file).

Processing order: `DATA:` blocks first (updating JSON), then `FILE:` blocks (updating Markdown), then `APPEND:` blocks (appending content verbatim), then `generate.py` runs automatically to refresh all `GENERATED:` markers. The updater script (`apply_changelist.py`) handles this sequence.

### DATA: blocks

Update any field in any JSON data file.

```
DATA: data/characters.json
PATH: Maelle.level
OP: SET
VALUE: 87
```

Fields:

- `DATA:` — repo-relative path to the target JSON file (required)
- `PATH:` — dot-notation path to the target field (required; see below)
- `OP:` — `SET`, `ADD`, or `REMOVE` (required)
- `VALUE:` — JSON value; must be last field; omit for `REMOVE` without value (optional)

`VALUE:` is parsed as JSON — so `true`, `false`, `null`, `42`, `"string"`, `{"a": 1}`, `["x","y"]` all work. Strings must be quoted.

**PATH syntax:**

| Syntax                              | Meaning                                                                    |
|-------------------------------------|----------------------------------------------------------------------------|
| `Maelle.level`                      | Key `level` inside key `Maelle`                                            |
| `pictos[name=Clea's Life].obtained` | Item in `pictos` array where `name == "Clea's Life"`, then key `obtained`  |
| `pictos_equipped[1]`                | Array item by integer index                                                |

Filter values (`[key=value]`) are always compared as plain strings.

**OP semantics:**

`SET` — create or update the value at PATH. Works whether the key exists or not.  
`ADD` — append VALUE to the array at PATH.  
`REMOVE` — three sub-cases:
- Path ends with `[filter]` or `[index]` → remove that item from the parent array (no VALUE needed)
- Path ends with a key + VALUE given → remove that value from the array at that key
- Path ends with a key + no VALUE → delete that key from its parent dict

**Examples:**

```
DATA: data/characters.json
PATH: Maelle.attributes.agility
OP: SET
VALUE: 99

DATA: data/pictos-lumina.json
PATH: pictos[name=Clea's Life].obtained
OP: SET
VALUE: true

DATA: data/playthrough.json
PATH: inventory.colour_of_lumina
OP: SET
VALUE: 150

DATA: data/characters.json
PATH: Maelle.lumina_extras
OP: ADD
VALUE: {"name": "Full Strength", "notes": "25% damage at full HP"}

DATA: data/characters.json
PATH: Maelle.lumina_extras[name=Full Strength]
OP: REMOVE

DATA: data/characters.json
PATH: Maelle.skills_learned
OP: REMOVE
VALUE: "Gommage"

DATA: data/characters.json
PATH: Maelle.notes
OP: REMOVE
```

### FILE: blocks

Section replacement at `###` level (or `##` level for full-section replacements). The updater script locates and replaces each section in the target file.

```
FILE: overview/claude-expedition33.md
SECTION: ## Section > ### Subsection
AFTER: ### Sibling (optional — only for inserts, specifies insertion point)
CONTENT:
### Subsection
...full replacement content...

```

- `SECTION:` uses `## Parent > ### Child` for `###`-level; `## Section` for `##`-level
- `AFTER:` is omitted for replacements; only used for new section inserts
- `CONTENT:` is the complete replacement text including the heading line
- Separators (`---`) between `##` sections are inserted automatically by the updater script — do not include them in `CONTENT:` or between FILE blocks
- Failure mode: loud — no silent corruption
- **Maintenance discipline:** `###` heading text must be unique within its `##` parent. Renaming a heading requires a direct file edit, not a changelist entry.

### APPEND: blocks

Verbatim append to the end of a file. Does not parse or reformat the file — no separator stripping, no blank-line normalisation, no `##` separator insertion.

```
APPEND: chats/chat-index.md
CONTENT:
| Chat 23 | [Formatted](...) / [Raw](...) | [chat23.md](...) | Summary text. |
```

- `APPEND:` — repo-relative path to the target file (required)
- `CONTENT:` — text to append verbatim; must be last field (required)
- Intended for flat-structure files where `FILE:` section targeting is not applicable: `chats/chat-index.md` (table rows) and `reference/historical-errors.md` (numbered list items)
- The script ensures the file ends with exactly one newline before appending

## Scripts

| Script          | File                     | Description                                                                                                                                                                                                                         |
|-----------------|--------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Updater         | `apply_changelist.py`    | Applies DATA:, FILE:, and APPEND: blocks from a changelist file. Calls `generate.py` after applying all blocks. Matt runs this on the changelist at end-of-session.                                                                 |

## Key Constraints

- Claude cannot intercept its own output stream — transcripts are written explicitly at each `!log` step
- SSH key is not accessible to Claude — `git push` is always done by Matt
- Compaction is detected visually in the UI, not programmatically; can be verified by checking `/mnt/transcripts/` for files — if noticed, trigger `!close` immediately
- `###` heading uniqueness within a `##` parent must be maintained for the updater script
- Part file split targets 500–600 lines per part; grouping is determined by the end-of-session pass
- Transcripts must be written verbatim — both Matt's turns and Claude's turns, including all pasted content
- Bracket notation is for tool calls only — `*[Fetched X]*`, `*[Created Y]*`. Never use brackets to represent substantive response text
- The `<!-- SECTION -->` marker must appear on a line by itself (no surrounding text) so the anchored `csplit` pattern matches correctly
- Changelists contain only `DATA:`, `FILE:`, and `APPEND:` blocks — no instructions, notes, or commentary
